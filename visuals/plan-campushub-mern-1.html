Index uniques porteurs d'invariants
utilisateurs.email : un compte par adresse reservations(trajet, passager) partiel sur CONFIRMEE : pas de double réservation inscriptions(evenement, utilisateur) : une inscription par étudiant avis.reservation : une note par trajet effectué messages(expediteur, clientId) : un renvoi ne crée pas de doublon notifications.cleDedup : un rappel par inscription
Index de lecture (< 1 s)
annonces(statut, categorie, prix) + index texte titre, matiere trajets(statut, dateDepart) + texte lieuDepart, lieuArrivee messages(cleConversation, createdAt) notifications(utilisateur, lue, createdAt) evenements(dateDebut), signalements(statut) Pagination ?page=&limit=, limite max 50
Temps et confidentialité
Dates stockées en UTC, affichées en Africa/Tunis (UTC+1, sans heure d'été) Tableau de bord : agrégats uniquement, aucun nom exporté vers le ML Activité quotidienne : activites(utilisateur, jour) upsert, pour « utilisateurs actifs » Suppression d'un compte : anonymisation + contenus masqués (pas de références orphelines)

Flux critiques

Les trois chemins d'écriture où un bug se voit le plus : surréservation, messages perdus ou dupliqués, prix conseillé indisponible.

sequenceDiagram
  autonumber
  actor E as Étudiant
  participant UI as SPA (TanStack Query)
  participant API as API Express
  participant DB as MongoDB (transaction)
  participant S as Socket.io
  E->>UI: clique Réserver
  UI->>UI: bouton passe à Réservé (optimiste)
  UI->>API: POST /api/trajets/:id/reservations {nbPlaces}
  API->>DB: startTransaction
  API->>DB: findOneAndUpdate trajet si OUVERT et placesDisponibles >= n, $inc -n
  alt places suffisantes
    API->>DB: insert Reservation CONFIRMEE (index unique trajet+passager)
    API->>DB: commit, statut COMPLET si 0 place
    API->>S: notification RESERVATION vers user:conducteur
    API-->>UI: 201 réservation
    UI->>UI: invalide trajets + tableau de bord
  else complet ou déjà réservé
    API->>DB: abort
    API-->>UI: 409 TRAJET_COMPLET ou DEJA_RESERVE
    UI->>UI: annule l'état optimiste + toast en français
  end

sequenceDiagram
  autonumber
  actor A as Étudiant A
  participant UA as SPA de A
  participant API as Socket.io (API)
  participant DB as MongoDB
  participant UB as SPA de B
  A->>UA: tape Entrée
  UA->>UA: bulle affichée en attente, clientId = uuid
  UA->>API: emit message:send {destinataire, texte, clientId}
  API->>API: vérifie session, non bloqué, longueur max 2000
  API->>DB: insert Message (unique expediteur+clientId)
  alt nouveau
    API->>DB: upsert Notification MESSAGE
    API-->>UA: ack {ok, message}
    API->>UB: emit message:new vers user:B
    UB->>UB: conversation remontée, badge non lus +1
  else doublon après reconnexion
    API-->>UA: ack {ok, message existant}
  end
  Note over UA,API: Coupure : socket.io se reconnecte, la SPA refetch depuis le dernier message puis renvoie les clientId sans ack

Questions ouvertes

Points que le cahier des charges ne tranche pas pour cette construction. Les choix sont enregistrés automatiquement.

Q1mobile
L'application mobile (APK) fait-elle partie de cette construction ?

Le cahier liste un APK Android en livrable. Il prévoit aussi une solution de repli : une version web responsive prioritaire si le mobile prend du retard.

Impact réel : l'API accepte déjà l'en-tête Bearer, donc une app Expo pourra s'y brancher plus tard sans rien changer côté serveur. L'inclure maintenant ajoute environ 30 % de travail et repousse la démo web.
Q2inscription
Faut-il vérifier l'e-mail avant d'utiliser l'application ?

L'UML inclut « Vérifier l'e-mail universitaire » à l'inscription. La question est de savoir si un compte non vérifié peut déjà naviguer.

Impact réel : en mode strict, la démo demande d'ouvrir Mailpit (localhost:8025) pour cliquer sur le lien. Les comptes du seed sont déjà vérifiés, donc la connexion de démo reste immédiate.
Q3événements
Qui peut publier un événement de club ?

Le cahier dit « les clubs publient », mais l'UML n'a que deux rôles (ETUDIANT, ADMIN) et un champ texte club.

Impact réel : si tout étudiant peut publier, n'importe qui peut créer un faux événement « Club IEEE ». La modération par signalement le rattrape, mais après coup.
Q4tableau de bord
Le tableau de bord analytique : dans l'app, dans Streamlit, ou les deux ?

Le cahier cite « Pandas, agrégations MongoDB, Streamlit / Plotly ». La maquette, elle, montre le tableau de bord dans la page Administration.

Impact réel : la page admin dans React suffit pour la démo. Streamlit est utile pour le rapport du membre Data, car il montre pandas et Plotly sur les mêmes données, mais c'est un quatrième serveur à lancer.
Q5déploiement
L'application doit-elle être en ligne à la fin de cette construction ?

Le cahier liste « application web déployée » et MongoDB Atlas. Le déploiement suppose des comptes et des secrets qui vous appartiennent.

Impact réel : le code est prêt pour la production dans les deux cas (variables d'environnement, Atlas compatible avec le replica set). Le choix porte seulement sur le fait que je crée ou non les fichiers de configuration d'hébergement maintenant.
Noteslibre
Autre chose à changer dans ce plan ?

Un module à retirer, une priorité à modifier, une contrainte du jury que je ne connais pas.
